## F59 - `pirx verify` refused a ledger the manual told you to produce

The gate topology has two processes by design. `pirx-gate` is long-lived: it
holds `<gate-dir>/ledger.jsonl` for the whole session. `pirx gate-approve`
opens **the same default path** - `book = gate_dir / "ledger.jsonl"` in
`cli.py` - for each queue walk, writes `gate.presented`,
`attention.challenge_issued`, `approval.decided`, and `grant.issued`, then
exits.

`Ledger.__init__` read the tail once and cached `_seq` and `_head` for the
life of the instance. So the pump's next append - `gate.forwarded_granted`,
the record that proves the call was authorised - reused a sequence number and
chained a head that four records had already superseded.

Measured, before the fix, on the manual's own sequence from §4.6:

```
0 gate.started
1 gate.pending
2 gate.awaiting_approval
3 gate.presented
4 approval.decided
5 grant.issued
3 gate.forwarded_granted        <- duplicate seq, superseded prev_hash

refusal.ledger_chain: ledger chain seam, line 7
```

This is worse than a broken audit trail, because a broken audit trail
announces itself once. What this produced was a control that fails **every
time the system is used as documented**, and the first thing a failure that
common teaches an operator is to stop running the verifier. A tripwire that
cries wolf on the happy path is worth less than no tripwire, because it also
consumes the credibility of the ones that are right.

Two properties made it invisible for three versions. The suite exercised one
writer per file, because through 0.6.0.0 there *was* one writer per file, and
the assumption was never written down anywhere a reviewer would trip over it -
it lived in the shape of `__init__`, not in the module's negative space (P2's
whole point). And `docs_audit.py` cannot see it: pins, markers, badges, and PT
numbering are all it checks, none of which is a claim about runtime.

**The fix is the one `spendstore.py` already uses: let the kernel arbitrate.**
Every append takes an exclusive `flock`, re-reads the real tail inside the
lock if the file grew since this instance last looked, chains from what is on
disk, and releases. The cached head survives as an optimisation behind a
length check, so the uncontended case stays O(1) and the contended case stays
correct.

The length check is deliberately an **append** detector and says so in the
code: an in-place edit preserving byte count is invisible to it, and that is
`verify_chain`'s job. A writer that tried to police the file it appends to
would be a second verifier with a weaker view than the real one.

**Named residual, added to PT9:** `flock` is advisory and local. The ordering
claim covers writers on one filesystem and nothing else. A shared or
networked ledger is the first networked transport and fires PT14's trigger
rather than arriving quietly.

The `fcntl` import is hard rather than guarded. A platform fallback to an
unlocked append would be a warning that lets execution continue, which is
what P11 exists to refuse; Windows already owes this project a launcher, and
now it owes it a lock too.

**Mutation run.** Replacing the refresh call with `pass` - the exact
pre-0.7.3.0 behaviour - fails both new tests and nothing else. The tests kill
the mutant that is the bug, not a mutant near it.

## F60 - three documents, three different clocks, one code path (OPEN)

Chasing F59 through the gate's two processes surfaced a second thing that
crosses the same boundary: the grant deadline.

- `grant.py`'s header announces, as a 0.7.0.0 consequence: **"Expiry moves to
  the wall clock."** It names the cost - an operator who rolls the system
  clock back extends a grant - and calls it a threat-model line.
- `grant.py`'s own **`Does NOT`** section, forty lines below, said expiry *is*
  monotonic and that a serialised grant is meaningless outside its process.
- `THREAT-MODEL.md` **PT4** said "Single process, so there is no clock to skew
  or roll back", which stopped being true at 0.7.0.0.
- Every wiring site - `cli.py`, `gate_approve.py`, `mcp/pump.py` - injects
  `time.monotonic`. The code never moved.

So a deadline written by `gate-approve` is compared against a reading taken in
`pirx-gate`. On Linux and macOS both anchor at boot and the comparison holds;
CPython documents the reference point as valid only within one process. The
property works by implementation detail, and the documentation describing it
is wrong in three different directions at once.

**Deliberately not resolved here.** Adopting the wall clock and accepting the
rollback exposure, or keeping monotonic and stating a supported-platform
constraint, are both defensible, and both change PT4's control text. That is
the owner's call, not something to settle by editing a docstring until it
matches whichever behaviour happened to ship. The header now says UNRESOLVED
and points at the TODO item; PT4 carries the correction and the open decision.

## F61 - the session budget's long-lived surface does not exist

`MAX_GRANTS_PER_SESSION = 20` carried a note saying its bite arrives with a
long-lived approval surface, "the gate, 0.7.0.0". The gate deliberately built
the opposite: `gate-approve` walks the queue once and exits, and
`gate_approve.py`'s own docstring rejects a resident daemon as "most of the
way back to a session".

A "session" is therefore one queue walk, and a fresh issuer starts each one.
The constant bounds a walk, not an operator's day. Corrected in place, with
the honest framing: it is a fatigue bound, not an authority bound, because
every grant in every walk still costs a passed challenge above the reading
floor. No code change - the behaviour is defensible, only the claim was not.

## What this sprint says about the process

Three findings, all from reading code against its own documentation, none
reachable by any check in the gate. Two of the three are the same failure
mode: a claim that was true when written, invalidated by a later version, in
a place the later version had no reason to open. F58 in 0.7.2.2 was the same
shape.

The generalisation is not "write more checks". It is that **a shipped version
which changes a topology owes a re-read of every claim that named the old
one**, and the project has no such step. Whether that becomes a checklist
item in the merge procedure or stays a habit is a decision, and it is in the
TODO with an owner rather than asserted here.

## Deliberately not done

- **A lock file, lease, or single-writer daemon**: rejected. `flock` on the
  file being appended is fewer moving parts than any of them, and the
  concurrency design is one syscall a reviewer can check.
- **Separate ledgers per process**: rejected. The gate flow's story spans both
  processes; splitting the file would make correlation a manual join and would
  trade a detectable break for a silent one.
- **Resolving F60**: rejected, above. Owner's decision.
- **A `docs_audit.py` check for docstring/code agreement**: rejected as
  unbuildable at honest cost. The three findings this sprint are prose claims
  about runtime; a check that could read them is a check nobody can trust.
