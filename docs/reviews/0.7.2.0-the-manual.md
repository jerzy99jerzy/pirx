# Review: 0.7.2.0 - the operator manual, and a tripwire under it

```
Document:     docs/reviews/0.7.2.0-the-manual.md
Scope:        docs/MANUAL.md v2.0, tools/manual_audit.py, the CI step and the
              two tests that measure it
Occasion:     pre-push review
Disposition:  per finding
Version:      0.7.2.0
```

0.7.1.0 shipped a 478-line manual that covered the happy path. This version
replaces it with a 900-line operator document and, more importantly, makes its
factual claims checkable.

Gate: ruff 0, mypy strict 0, **206 tests**, docs audit clean, manual audit
clean.

## The problem a manual creates

Every other document in this repository is read by someone who can check it
against the code: a reviewer, a maintainer, the author six months later. The
manual is the first document written for someone who **cannot** - an operator
reads "the grant lives five minutes" and acts on it. A manual whose facts have
drifted is worse than no manual, because it is trusted exactly where it cannot
be verified.

So the manual's checkable claims are checked. `tools/manual_audit.py`
verifies:

- every constant the manual quotes matches the code, **including its
  formatting** - a table saying `2000` where the standard is `2 000` has been
  hand-edited and may have been edited wrongly;
- every refusal type declared in `errors.py` appears in the manual;
- every ledger event emitted anywhere in `pirx/` appears in the manual;
- the worked floor arithmetic in §12 still evaluates to the number printed.

It runs as its **own step inside the `docs-audit` job**, not as a new job.
That is a deliberate choice with a trade-off worth naming: a separate job
would have meant a fifth required status context and a branch-protection
change, which is a settings edit that has to be made by hand and remembered.
As a step it fails the `docs-audit` context, and the step name puts "manual
audit" in the log rather than burying it - the failure is still findable, and
nothing about the merge gate had to be reconfigured. It is also a test
(`test_manual_audit_passes`), so a local `pytest` catches drift before CI
does.

Its own failure mode is measured, per the F9 lesson: a test drifts a constant
in a copied tree and asserts the audit exits 1 naming the constant.

**What it does not do**, stated so nobody reads more into a green check: it
verifies numbers and names. It cannot verify that the prose around them is
true. §6.1's reading order and §7.5's threat analysis are unchecked by
anything but review.

## What the audit found on first run

One gap: `refusal.unspecified`, the default `event` on the base `Refusal`
class, was undocumented. It is not a real refusal type - no subclass uses it -
so the fix was not to add a table row pretending it is one. The manual now
carries a short "one event you should never see" note: if it appears in a
ledger, a refusal type was added without naming its event, which is a defect
in Pirx rather than a condition in the operator's environment.

That is the audit doing exactly its job on day one, and the reason it is worth
having.

## What the manual gained over v1.0

- **Topology as a first-class choice** (§3), including the two costs of the
  split - wall-clock expiry and a copyable grant - stated as costs.
- **Key management** (§7): rotation as three deliberate steps rather than a
  command, and an honest account of what a stolen key does and does not buy.
  The answer - approve without a human, once per distinct action, visibly - is
  more useful than a warning.
- **Directory lifecycle** (§9), with `spent/` marked explicitly unsafe to
  prune, because an automatic prune of a spend record is a replay window with
  a timer on it.
- **Recovery procedures** (§10), including the instruction not to repair a
  broken ledger. A repaired ledger is one nobody can rely on afterwards.
- **Monitoring** (§11), split into alert-on and trend-on, and naming the alert
  nobody can write from inside Pirx: an action in the target system with no
  corresponding grant event anywhere.
- **Three reference sections** (§12-15) generated against the code and now
  pinned by the audit.
- **A glossary**, because the vocabulary is load-bearing and was previously
  only defined inline in docstrings a user never reads.

## Improvements deliberately not taken

- **Generating the reference tables from the code at build time**: rejected.
  A generated table is always correct and therefore never read by its author;
  a hand-written table with a tripwire under it is read once and then
  defended. The failure the audit catches is the one worth catching.
- **Documenting the 2025-era MCP workaround**: rejected, because there is no
  workaround. §16 says the limitation is real and why the alternative is
  worse, which is the honest answer to the most likely first support question.
