# Pre-push review: 0.3.0.0 first capability

```
Document:     docs/reviews/0.3.0.0-first-capability.md
Scope:        pirx/adapters/, pirx/capability.py, pirx/reconcile.py,
              pirx/session.py, pirx/registry.py, pirx/cli.py, tests/harness/
Disposition:  per finding - fixed / accepted with reasons / deferred
```

This is the version where Pirx can write. Everything below either widens the
write surface deliberately or narrows something that would have widened it by
accident.

## F11 - The import scrape was blind to subpackages - **fixed**

`modules()` used `PACKAGE.glob("*.py")`, which sees only the top level. The
first network import in this project's history landed in `adapters/jira.py`
in this very sprint, in a directory the scrape did not read. The network
allowlist test would have kept passing while the package gained an
unrestricted HTTP client.

Fixed: `rglob`, allowlist entries keyed by package-relative path
(`adapters/jira.py`), and a dedicated test asserting the subpackage is
actually scanned - so if the blind spot returns, that test fails before the
network check silently starts passing again.

This is the sharpest lesson of the sprint: **a scrape with a blind spot is
worse than no scrape**, because the green tick is read as coverage. The check
was written in 0.1.0.0, passed for two versions, and was structurally unable
to see the thing it existed to catch the moment that thing appeared.

## F12 - Banning the `os` module outright would have hidden credential
reading in a worse place - **fixed by naming the surface**

`os` was on the process-reach blocklist. Reading `PIRX_JIRA_*` from
`os.environ` in the runner therefore failed the build. The tempting fixes
were both bad: allowlist `cli.py` for process reach (widening the wrong
thing), or read credentials some other way (a config file to parse, a
keychain call, a discovery routine - all larger attack surface than
`os.environ`).

Fixed by judging `os` on attribute rather than import: `os.system`,
`os.popen`, `os.exec*`, `os.spawn*`, `os.fork` and relatives are process
reach; `os.environ` is not. Same shape as the read/write sharpening in F8:
when a check is too blunt, sharpen the check rather than widen the
exception.

## F13 - A17 measured a weaker property than its docstring claimed -
**fixed, found by mutation**

`test_a17_intent_written_before_the_write` asserted that `capability.attempt`
precedes `capability.result` in the ledger. A mutant that moved the write
*before* the attempt record still satisfied that: both events still land in
that order, they just land after the fact. The test's name and docstring
claimed "intent recorded before the action"; the assertion did not measure
it.

Fixed by observing from the adapter's vantage point: `RecordingAdapter` takes
a callback invoked during `comment()`, capturing what the ledger already held
when the write began. The mutant now fails the test. Same rule as everywhere
else in this codebase - the claim and the measurement must be the same claim
(P7).

## F14 - Stale bytecode can produce a false result after a mutant is reverted
- **accepted with reasons, procedure amended**

Reverting a mutant with `cp` left `__pycache__` holding the mutated module,
producing a red result for correct code. The same mechanism can produce the
more dangerous outcome - a **green** result for mutated code - which would
make a mutation run worthless while looking rigorous.

Accepted rather than automated: the mutation procedure is deliberate and
manual (see 0.2.0.0 review, F9). The procedure now requires clearing
`__pycache__` between mutant and revert, and re-running the full suite after
reverting rather than trusting the mutant run's inverse. Recorded here
because the next person to run mutants will hit it, and a false green is not
a nuisance, it is a wrong conclusion about a control.

## F15 - Jira reachability is not tested, and must not appear to be -
**accepted with reasons**

`tests/harness/test_jira_adapter.py` drives the adapter through an injected
transport. It measures what this codebase controls: HTTP method, URL
construction, header set, credential encoding, request body shape, the
idempotency trailer, response-to-outcome mapping, and that the token never
reaches a URL or a body. It does **not** measure that a real Jira accepts any
of it.

Accepted because the alternative is a CI job that needs a live tenant and
credentials, which trades a named gap for a secret in the pipeline. The gap
is named here, in the adapter's docstring, and in README. Trigger for
revisiting: the first time a schema change on Jira's side breaks production
without the suite noticing - at which point a contract test against a
recorded response corpus becomes owed, not a live-tenant test.

An earlier draft of this suite contained a vacuous assertion
(`"tok" not in ""[:0] + ""`, trivially true) that appeared to check
credential leakage. It was replaced with a real one before the sprint closed.
Noted because a passing test that measures nothing is the exact failure mode
this project's rules exist to prevent, and it got written anyway.

## F16 - 0.2.0.0 has no bump commit and no tag - **accepted with reasons**

The harness (0.2.0.0) and the first capability (0.3.0.0) reached the
repository in one pull request, because 0.3.0.0 modified files 0.2.0.0
introduced - the scrape, the harness, `session.py` - and no intermediate
working tree existed that would have passed its own gate. Reconstructing one
to justify a tag would have manufactured history rather than recorded it.

Consequence, stated rather than hidden: `v0.2.0.0` does not exist as a tag,
and the version plan's shipped row for it is satisfied by content, not by a
ref. Trigger for not repeating this: one pull request per version from
0.4.0.0 onward, so the version bump commit and its tag have somewhere to
land.

## F17 - Rebase merge drops the empty version-bump commit - **fixed for
0.4.0.0 onward; 0.3.0.0 tag stands where it landed**

Section 8 requires the version bump to be its own commit. It was created as
an **empty** commit, because the actual version changes - `pyproject.toml`,
`pirx/__init__.py`, `STATUS.json` - had already been folded into the feature
commit. GitHub's rebase merge discards empty commits, so `chore: version
0.3.0.0` does not exist on `main` and `v0.3.0.0` tags a feature commit.

The repository setting is not the defect. Rebase merge was chosen precisely
to preserve the two-commit shape, and it did exactly what it says. The defect
is the commit pattern: an empty marker commit carries no content and so has
nothing to survive on.

Fixed for 0.4.0.0 onward: the version bump commit **contains the version
change and nothing else**. Feature commits leave `pyproject.toml`,
`pirx/__init__.py`, and `STATUS.json` at the previous version; the bump
commit changes them. It is then non-empty, survives rebase, and the tag names
a commit whose diff is the version.

`v0.3.0.0` is left pointing where it does. Moving a published tag to
retrofit a convention would be rewriting history to make a document true,
which is the inverse of what this project's rules are for.
