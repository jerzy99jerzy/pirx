## Why this version exists

The repository sat still for six weeks on items recorded as "either is fine,
silence is not". Each cost under half an hour once chosen. A decision with two
acceptable outcomes and no forcing function does not schedule itself, so this
version takes them, and takes them as one PR so the next one starts from a
repository that has moved.

## The decisions

**FAMILY.md's canonical home: cve-digest, recorded rather than chosen.** The
working recommendation going into this version was the opposite - name Pirx
the home, because the exchange directory, `CONTRACT.md`, and the matrix live
here. Reading cve-digest at `786efcd` overturned it: that repository's
estate-layer brief, landed at 0.7.14.4 on 2026-09-03, already names FAMILY.md
as a deliberate forward reference landing after its 0.8.0.0 gate. The
decision had been made and never carried back. Choosing Pirx here would have
meant a second, conflicting decision about a shared document, taken from one
side. The argument that the machinery exists only in Pirx also does not
distinguish the options: FAMILY section 3.1 requires `docs/exchange/` in both
repositories whichever holds the document. FAMILY.md 1.2 records the home and
the interim rule; PX-0002 carries the amendment to the landing.

**WORKFLOW.md is not vendored (F32 closed).** Measured rather than argued:
upstream moved from 1.6 to 1.7 six days after PX-0001 read it. Pirx's
procedure is `docs/MERGE-PROCEDURE.md`, repository-scoped by its own header,
and FAMILY 3.5 now says workflow documents are not shared.

**Checkers raised to 3.14.** `requires-python`, the brief, and all four CI
jobs said 3.14 while ruff targeted `py312` and mypy `3.12`. Raised; both clean
with no source change (ruff 0.16.8, mypy 2.3.1; CI installs both unpinned).

**The topology step is a checklist line.** F58, F59, and F60 were one defect
three times, so it sits in MERGE-PROCEDURE.md 1.1 as a pre-push line rather
than an intention.

**Plan-row drift gets a check.** Check 8: every version README marks shipped
has a row in brief section 6. One-directional by design, since the brief
plans ahead of README. Its failure is measured by removing the 0.7.2.0 row, the
exact case brief v1.7 found by reading; separately, deleting the call from
`main()` fails that test.

## Checked, and not changed

The claim that the documented local gate skips the documentation audits was
tested and is false: `tests/test_docs_audit.py` runs both audits as

never mentioned the manual audit, and README enumerated four of seven audit

## F62 - the consumer has never accepted what the producer emits

The first diff of cve-digest's emitter against `CONTRACT.md`, done by building
a payload with the producer's own `build_verdicts` at 0.7.18.0 and handing it
to `pirx.consumer.parse`. Refused whole, for two independent reasons:

- `vex_status: "none"` is cve-digest's default for every CVE without an
  operator VEX statement, since its 0.7.0 (2026-07-27). `VEX_STATUSES` does not
  contain it. `EnumRefusal`.
- `score` is validated against [0.0, 100.0]. The published schema carries only
  `minimum: 0.0`, because KEV items start at 100.0 and go above it; the test
  payload's KEV item scored 109.1. `BoundsRefusal`, and
  `test_out_of_range_numbers_are_refused` asserts that 101.0 must be refused,
  so a test encodes the wrong contract.

Cause: the field table was written from brief v1.2's prose, and
`examples/verdict-sample.json` was written by hand with every item at
`"affected"` and a non-KEV score. Nothing on the verdict path has ever been
fed emitter output. The failure is closed - Pirx refuses, it does not
mis-accept - so no control is unsound. What is false is the claim that Pirx
consumes `cve-digest.verdict/1`, and anyone holding both repositories could
show it in minutes. **Disposition: deferred to the next PR**, owned in TODO,
with a producer-emitted fixture carried by hand.

## F63 - additive fields meet an untested tolerance

cve-digest 0.7.18.0 (2026-09-24) added `epss_pending` and `epss_percentile`
under the same schema id. Pirx accepts the payload only because `_verdict`
reads known keys and ignores the rest - behaviour no test states, now load
bearing. And for a pending item, `epss: 0.00000` enters the rendered bytes the
approver reads as though it were a measurement, which the producer's schema
now explicitly tells consumers not to do. **Disposition: deferred to the next
PR**, with the render-or-refuse choice named in TODO. The producer-side half
is not Pirx's to fix: the schema declares `additionalProperties: false`, so
adding properties breaks any consumer validating against an earlier copy -
the schema's own stated criterion for a breaking change. That travels as
PX-0003.
