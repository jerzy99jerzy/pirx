# Review: 0.6.0.0 - the justification abstraction

```
Document:     docs/reviews/0.6.0.0-justification-abstraction.md
Scope:        pirx/justification.py, the renderer's delegation, the proposer's
              use of adapter #1, CONTRACT's new section, the README position
              marker and its audit check, harness A36
Occasion:     pre-push review of the sprint, per section 8 conventions
Disposition:  per finding - fixed / accepted with reasons / deferred
Version:      0.6.0.0
```

The sprint's claim is deliberately narrow: **a seam exists for a second
evidence source, and the verdict path produces the bytes it produced before
the seam existed.** The second half is the load-bearing one - a refactor of
the hash preimage silently voids every grant scope the project has ever
issued, and "the tests still pass" is a weak proof when the tests were
written against the code being refactored.

Acceptance criterion, set before the work and met: **the 156 tests that
shipped with 0.5.0.0 pass unmodified.** Not one was edited to accommodate the
abstraction. On top of that, `test_justification.py` holds the rendering as a
literal golden preimage, because unmodified tests prove only that nothing
changed *that they looked at*.

Gate: ruff 0, mypy strict over `pirx/` 0, 167 tests, docs audit clean.

## F41 - "Tests pass unmodified" is a weaker claim than it sounds -
**fixed by adding golden bytes**

The existing proposal tests compute the expected rendering from the same
function they test, so a systematic change to that function moves the
expectation with it. They would have passed had the renderer emitted
`justification: <id>` instead of `verdict: <id>` - and every action hash in
the project would have changed silently. `GOLDEN` in
`tests/test_justification.py` is the byte string, written out, which is the
only form of this claim that cannot move on its own.

## F42 - The evidence digest exists and does nothing yet - **accepted, and
made executable**

`Justification.digest` is computed by adapter #1 and is not in the preimage.
A field that looks like a control but is not covered by the hash is exactly
the shape P7 forbids, so the acceptance is asserted:
`test_digest_is_carried_but_not_hashed_yet` fails if the digest ever appears
in the rendered bytes without a new render schema id. Owner for making it
load-bearing: 0.7.0.0, where it binds the grant to the tool definition in
force at approval time (PT16). Putting it in `/1` now would be a wire-format
change wearing a refactor's clothes - the same defect F41 guards against.

## F43 - Two fields could name the same thing with two answers - **fixed at
construction**

`Proposal` carries both `verdict` and `justification`. A verdict-labelled
justification whose `ref` differs from `verdict` would render one id while
downstream code read another: substitution (PT5) one field to the left of
where PT5 looks for it. Rejected in `__post_init__` as a `TypeError`, so the
object cannot exist, rather than refused at spend where a human has already
been shown the wrong reason. Harness A36 asserts it and asserts that nothing
reached the ledger.

The alternative - dropping `verdict` in favour of `justification.ref` - is
the right end state and is not this sprint's, because it changes
`Grant.verdict` and the ledger's field names, which is behaviour. Owner:
0.7.0.0, when adapter #2 forces the question anyway.

## F44 - The README position marker was a prose claim - **fixed by pinning it
to the audit**

"You are here: 0.6.0.0" is the line a reader trusts for orientation, and a
version written in prose goes stale on the first bump that forgets it. The
docs audit now requires exactly one marker and requires it to equal
`STATUS.json`'s version; the check's own failure mode is measured
(`test_docs_audit_detects_a_stale_position_marker`), per the F9 lesson. The
`Since` column in the inversion table is the same discipline applied to the
properties themselves: a reader can see which claims were true at which
version instead of reading the table as a flat present tense.

## Improvements deliberately not taken

- Making `JustificationSource` an ABC rather than a `Protocol`: rejected. An
  ABC would require the gate's source to import Pirx's core to inherit from
  it; a Protocol keeps the dependency pointing inward.
- Hashing prose into the evidence digest: rejected, and
  `test_evidence_excludes_prose` fixes the decision in place. A digest over
  model-authored text makes a verdict's evidence identity depend on what a
  model wrote about it (PT2).
- Renaming `pirx.proposal/1` pre-emptively "since /2 is coming": rejected.
  Ids are retired, never redefined in advance (P8).
