# Full-repository review: 0.4.0.1

```
Document:     docs/reviews/0.4.0.1-full-review.md
Scope:        the entire repository as of v0.4.0.0 - all of pirx/, tests/,
              docs/, CI, and the day's operational record
Occasion:     four versions shipped in one day; a deliberate stop to read
              everything as a whole before 0.5.0.0
Disposition:  per finding - fixed / accepted with reasons / deferred
Version:      changes here ship as 0.4.0.1 (micro: fixes, no new surface)
```

Method: every module read end to end against its own docstring register;
every claim in README and THREAT-MODEL checked against a test that measures
it; the day's git and CI history mined for procedure defects; fixes verified
by mutation where the defect was behavioural.

## Findings

### F23 - A model refusal mid-run crashed the runner and truncated the audit
trail - **fixed, verified by mutation**

`cli.run` wrapped `session.consume` and the grant/execute steps in
try/except, but not `session.propose` - the step that gained a failure mode
when the model entered at 0.4.0.0. A `ModelRefusal` there propagated as a
traceback: no `run.finished` event, no exit status, a ledger that stops
mid-sentence. The refusal event itself *was* recorded (the session writes it
before re-raising), which made the gap easy to miss - the ledger looked
almost right.

Fixed: the propose step now ends the run honestly (`run.finished`, exit 2,
message on stdout). Attack A30 asserts all three, and reverting the fix
turns A30 red. Exit 2's meaning widened accordingly: *refused before any
approval*, whether at the payload boundary or at the model's contract.

The general lesson, recorded because it will recur: **when a step gains a
new failure mode, the caller's error handling is part of the change**, not
an implementation detail the type checker will catch - `Refusal` is a
`raise`, not a return type.

### F24 - Ledger appends were not durable - **fixed, measured**

`capability.attempt` is the record the at-most-once story leans on: it must
be on disk *before* the adapter is called, or a host crash yields an action
with no attempt - which PT9 treats as evidence of tampering, misdiagnosing
an outage as an attack. Appends went through the page cache with no flush
and no fsync, so that ordering held against a process crash but not against
a host crash.

Fixed: every append flushes and fsyncs before returning. A test measures the
fsync (monkeypatched, call-counted) rather than trusting the docstring. Cost:
a few syscalls per event on a pipeline whose bottleneck is a human reading a
terminal. Residual, still named in `ledger.py`: fsync does not survive every
storage stack's lies, and tail truncation remains undetected - the remote
sink in the deferral table buys both.

### F25 - THREAT-MODEL.md described the pre-model world - **fixed**

PT2's entry still said "in 0.1.0.0 there is no model in the loop at all" and
PT6's said the fence was a future requirement - three versions of drift in
the document whose entire job is to be current. Both rows now describe the
shipped controls (exact-match selection, refusal without fallback, the
model-boundary import test, the deterministic fence with origin labels) and
name the harness attacks that measure them. Rule reaffirmed: a threat-model
row changes in the same PR as the control it describes.

### F26 - ARCHITECTURE.md carried an unpaid amendment debt from F3 -
**fixed**

Review F3 (0.1.0.0) accepted a deviation - action names from `KNOWN_INTENTS`
rather than an enum over registry keys - with the note "ARCHITECTURE.md
carries this as an amendment at its next bump (A13)". Three versions later
the bump had never happened. Now v1.1: A13 (the F3 deviation), A14 (the
deterministic fence tag, and why the approval frame stays random while the
in-preimage fence cannot be), A15 (the fsync decision). A promise to amend a
document "at its next bump" is a deferral with no owner unless the bump has
a trigger; the honest form is to amend in the same PR or put a version on it.

### F27 - Mermaid diagrams were unreadable in dark mode - **fixed**

The README and ARCHITECTURE diagrams carried no styling, so GitHub's dark
theme rendered the ledger cylinder near-white with light text on it. All
three diagrams now declare `classDef default` with dark fills and light
text, and the ledger node gets the same explicit style the brief's diagrams
have used since v1.0 - which is also the consistency point: the repository
already knew how to do this, in one document but not the others.

### F28 - Dead test fixture - **fixed**

`conftest.test_registry` had no remaining users; every attack now runs
against `PRODUCTION_REGISTRY` or an explicit empty registry. Removed. The
`TEST_ACTION` constant stays - the harness asserts it is absent from the
production registry, which is a live check, not a leftover.

## What was read and found sound

Recorded so the review says what it covered, not only what it caught:

- **Grant lifecycle** (`grant.py`): verification order puts replay before
  expiry (the stronger signal wins), the nonce burns before the caller can
  act, `SpentGrant` still has exactly one constructor. Mutation history from
  0.2.0.0 still applies.
- **Renderer determinism** (`proposal.py`): one serialisation, hash over
  bytes, fence tag content-derived. A29 pins byte-identity with hostile
  fence-shaped prose.
- **Scrape integrity** (`test_no_capabilities.py`): rglob over subpackages,
  network allowlist as a literal two-entry set, `os` judged by attribute,
  refusals catch-and-reraise enforced with `cli.py` as the single terminal
  site. The scrape's own blind-spot test (F11's regression guard) passes.
- **Adapter and model clients**: request construction measured against
  injected transports; credentials never in URLs or bodies; both refusal
  taxonomies (Pirx declining vs the far side failing) kept distinct.
- **CI**: actions pinned to SHAs, `permissions: contents: read`, three
  required contexts matching the job names (restored after F22).

## Improvements proposed, not implemented

Each with an owner, per P12 - and two rejected outright so they do not
return.

1. **`pirx verify <ledger>` subcommand** - owner: **0.5.0.0.** The chain
   verifier exists but is invoked via `python -c`, which contradicts the
   project's own P13 ergonomics: the verification everyone should run after
   every run is the hardest command to type. One subcommand, zero new
   surface (the verifier is already written and allowlisted).
2. **Structured JSON output for `reconcile`** - owner: **0.5.0.0,** with the
   second capability, when reconcile gains a second adapter to speak to.
   Today's prose lines are fine for a human; a SIEM ingesting outcomes will
   want the same fields the ledger holds.
3. **Property-based generation for the consumer** - owner: **the deferral
   table**, entered with "first schema change to verdict/*" as its trigger.
   The attack catalogue covers the threat model, not the input space; a
   schema migration is the moment that distinction starts costing.
4. **Rejected: dependency-audit CI step.** The runtime dependency set is
   empty by design - stdlib only - so the step would audit the test tooling
   and teach the reader that a green tick means supply-chain coverage it
   does not have.
5. **Rejected: auto-refreshing action pins or mutation tooling in CI.** Both
   already refused in TODO.md's rejected list; restated here because a
   full review is exactly when they get re-proposed.
