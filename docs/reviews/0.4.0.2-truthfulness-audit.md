# Truthfulness review: 0.4.0.2

```
Document:     docs/reviews/0.4.0.2-truthfulness-audit.md
Scope:        the repository read for a specific defect class - claims made
              without verification, and promises recorded without owners
Occasion:     asked directly where the record overstated what had been done
Disposition:  per finding - fixed / accepted with reasons / deferred
Version:      0.4.0.2 (micro: corrections and one new gate check)
```

The other reviews in this directory look for defects in the software. This
one looks for defects in *the record about* the software, because a project
whose central rule is "claims are measured, not asserted" (P7) is one where
an unmeasured claim is a defect of the same kind as a missing control - and
several accumulated while that rule was being enforced against the code.

The pattern is worth naming before the findings, because it is what makes
them predictable rather than random: **every failure below sits where
verification would have required leaving the working environment** - the
other repository, a vendor's API, the operator's own machine. Inside those
boundaries the record is accurate and measured. Outside them, plausible
narrative substituted for checking, and did so without flagging that a
substitution had occurred.

## F29 - The 0.4.0.1 review overstated its own method - **fixed in place**

Its opening claimed "every module read end to end against its own docstring
register; every claim in README and THREAT-MODEL checked against a test that
measures it". The first clause was true of `pirx/`. The second was not: had
it been done, F31 (a gate check claimed for four versions and never written),
F32 (a vendored document that does not exist), F33 (an architecture row
contradicted by the test it specifies), and F34 (a documented directory
absent from the repository) would all have surfaced there rather than here.

Fixed by correcting the method paragraph in the document itself rather than
appending a note, so a future reader is not asked to reconcile an accurate
correction with an inaccurate original. The finding stays here as the record
of what happened.

This is the most serious entry in this file. A review that overstates its
coverage is worse than no review, because it converts an unexamined area into
one the reader believes was examined - the same failure shape as F11's blind
scrape, applied to prose.

## F30 - `find_comment` reads one page of Jira comments - **accepted, with a
trigger**

Reconciliation searches the issue's comments for its idempotency trailer via
`GET /rest/api/3/issue/{key}/comment`, which Jira paginates at 50 by default.
On an issue with a long history the trailer can sit beyond the first page and
reconciliation reports "did NOT land" for a comment that landed.

Accepted rather than fixed: the comment being sought was created by Pirx
moments earlier, so it is near the tail, and the failure direction is safe - a
false negative sends a human to approve fresh work rather than silently
suppressing a real one. Trigger for fixing: the first observed false
negative, or the first adapter for a system with a smaller page size. Named
in the adapter's docstring, not only here.

Found while verifying the adapter's API shape against Atlassian's published
v3 documentation - a verification that should have happened when the adapter
was written.

## F31 - The docs audit was claimed in the gate for four versions and never
existed - **fixed**

Brief section 8 has listed a docs audit in the local gate since 0.1.0.0, and
FAMILY.md 3.5 rests the vendoring rule on it. No such check existed. It was
noticed once, given "0.2.0.0" as an owner in conversation, not built, and
never entered in the deferral table - so it became precisely the unowned
deferral P12 forbids, inside the document that forbids it.

Fixed: `tools/docs_audit.py` now runs in CI as a fourth required job and in
the local suite. It checks pin consistency between `STATUS.json` and the
versions documents declare, review coverage for every version README marks
shipped, agreement between the catalogue's row count and the suite's
assertion, and PT numbering for gaps or duplicates.

Verified by mutation before being trusted - four mutants (bad pin, extra
catalogue row, renumbered PT, a version marked shipped with no review), four
failures, restored clean. It then immediately caught a real mismatch created
minutes later in this same changeset, which is the best evidence it works
that a check can offer.

## F32 - `WORKFLOW.md` was declared vendored and does not exist - **fixed by
withdrawing the claim**

The brief's header read "inherits WORKFLOW.md from cve-digest verbatim,
v1.4", `STATUS.json` pinned `workflow: 1.4`, and FAMILY.md P13's provenance
cited it. No such file is in this repository and the author of this record has
never read it.

Fixed by withdrawing rather than fabricating: the header now says the
conventions in section 8 were adopted from cve-digest practice and that no
WORKFLOW.md is vendored here; the `workflow` pin is removed from
`STATUS.json`. Vendoring it for real is a human act requiring the actual
document, and belongs to exchange entry PX-0001.

## F33 - ARCHITECTURE 4.2 specified an attack whose delivered test asserts
the opposite - **fixed by amending the document, not the test**

The 1.0 sketch for the cross-run authority attack said "assert it is
unusable", reasoning that "hash preimage cannot be reproduced without the
run's proposal". That reasoning is wrong: rendering is deterministic by
design, so the preimage reproduces exactly. The delivered A11 correctly shows
a grant *succeeding* against a fresh issuer and documents the residual, which
is why HMAC grants and a durable spend store are coupled.

The document was amended to match the test. Recorded because the temptation
runs the other way - a test that contradicts a design document reads like a
failing test, and "fixing" it would have replaced a true statement about the
system with a false one that the document happened to predict first.

## F34 - `docs/exchange/` was documented and absent - **fixed**

README and FAMILY.md both name the directory; git does not track empty
directories, so it was never in the repository. A `.gitkeep` now creates it
and states what it is waiting for.

## F35 - FAMILY.md carried provenance nobody verified - **fixed by labelling**

The document's own rule is that a practice earns its place by having shaped a
real decision, with provenance. Five provenance lines cite Rappaport - its
docstring convention, its sink discipline, its refusal to expose ranking
weights, the verdict/1 discipline, the inherited WORKFLOW.md. All were written
from the project brief and the author's account; none were read out of that
repository, which the author of this record has never seen. The document was
also drafted inside Pirx, not in its declared canonical home.

Fixed by labelling each unverified line `[cve-digest: confirm]` and stating
the situation plainly in section 2's preamble. Not fixed by deleting them -
they may well be accurate, and deleting a possibly-true provenance line is
its own distortion. Confirming or striking them is the substance of exchange
entry PX-0001, which now has a concrete reason to exist beyond testing the
protocol.

## What this review does not claim

It read `pirx/`, `tests/`, `docs/`, CI configuration, and this repository's
own history. It did **not** read cve-digest, exercise either vendor API
against a live endpoint, or verify anything about the operator's local
environment beyond what appeared in terminal output during the day. Those
remain the three boundaries where this record's accuracy depends on someone
else checking - and, per the pattern named at the top, they are exactly where
it has failed before.
