# Review: 0.7.1.0 - the stdio pump, and the manual

```
Document:     docs/reviews/0.7.1.0-the-pump.md
Scope:        pirx/mcp/pump.py, the `pirx-gate` console script, harness
              A44-A47, the scrape's process-reach rule, and docs/MANUAL.md
Occasion:     pre-push review
Disposition:  per finding - fixed / accepted with reasons
Version:      0.7.1.0
```

0.7.0.0 shipped the gate's whole decision path and no way to run it. This
version closes that: `pirx-gate` is a process, verified end to end against a
real child over real pipes, and the documentation that described it in the
present tense is now accurate.

Gate: ruff 0, mypy strict 0, **204 tests**, docs audit clean.

## F55 - an oversized frame's tail was read as a new frame - **fixed**

`readline(MAX_FRAME_BYTES + 1)` stops mid-line when a peer sends something
past the bound. The first cut of the pump refused that first chunk and then
looped, reading the *remainder of the same line* as a fresh frame. A peer
could therefore hide a well-formed `tools/call` behind a megabyte of padding
and have the bounds check smuggle it in rather than refuse it - the check
turning into the delivery mechanism.

Fixed by draining to the end of line before continuing. Attack A45c asserts
the smuggling case directly ("a frame hidden behind padding was executed"),
and a mutant that removes the drain is killed by it. Found by a test written
before the code was trusted, which is the only reason it was found at all.

## F56 - the scrape's process-reach rule had to bend, and was restated -
**accepted, with a new assertion**

`test_no_process_or_shell_reach_anywhere` forbade `subprocess` in every
module. The pump must spawn the downstream server, so the rule could not stand
unchanged. It was **not** widened by adding a filename: the rule it enforces
is now written down as the property that actually matters -

> the only argv the pump may spawn is the one the operator typed at launch.

Nothing from a payload, a verdict, a tool definition, or a model may reach it.
`test_the_pump_spawns_only_operator_supplied_argv` checks this structurally:
exactly one `Popen` in the module, its command taken from the stored
constructor argument rather than an expression built at the call site, no
`shell=` keyword, and `DownstreamProcess` constructed exactly once from a name
bound to a slice of argv. An allowlist entry with no accompanying assertion is
how a rule becomes a name.

## Design decisions worth recording

- **The pump is synchronous.** One frame in, one frame out, in order. The gate
  holds a call until a human decides, so concurrency buys nothing here and
  costs something: an asynchronous pump could let an ungated call overtake a
  held one and land first, and the ledger's order would stop matching what
  happened.
- **A dead downstream is not a refusal.** `DownstreamGone` is a plain
  `RuntimeError`, deliberately not a `Refusal`: nothing was refused. Answering
  a caller with a JSON-RPC error would tell it a decision was made. The pump
  records the fact and exits 74.
- **The pump never restarts the child.** A supervisor that silently respawned
  a crashed server would hide exactly the crash the ledger exists to show.
- **stdout carries protocol only**, asserted by A47: every line the pump
  writes there parses as JSON-RPC. Diagnostics go to stderr, which is also
  where the specification points stdio servers.

## docs/MANUAL.md

The project's first operator-facing document. Everything before it was written
for a reviewer or a future maintainer; nothing told a person how to run the
thing and what to do when it stopped.

Two sections carry more weight than their length suggests. **§4, the approval
itself**, is the only place that explains what the framed bytes are, why the
boundary marker is random, and why a fenced block is not a decision input -
the things an operator has to understand for the whole design to mean
anything. **§7, the refusal table**, maps every typed event to its usual cause,
because a control that refuses without telling you why gets disabled by the
third person who meets it.

The manual states the comprehension limit in the same words the threat model
uses, and it says plainly that approvals cannot be scripted. Both are places
where a manual would ordinarily soften, and softening either would sell the
control as more than it is.

## Improvements deliberately not taken

- **A `--version` or self-test command**: rejected. A self-test that passes
  tells an operator less than a run that stops honestly, and the honest first
  run already exists.
- **Auto-restarting the downstream**: rejected, see above.
- **A `--gate-all` flag for the registry**: rejected. Registering a gated tool
  is a code change with a reviewed definition hash; a flag that gates
  everything would also be a flag that gates nothing, and it would arrive with
  no pinned hashes at all.
