## Badges are claims, so they are checked

The README previously carried one badge (the CI gate) and it was self-updating.
This version adds nine, and seven of them carry a number or a version - which
means seven new opportunities to be wrong in the most-read part of the
repository. A stale badge is read by everyone who never opens the file behind
it.

So `tools/docs_audit.py` gained `check_badges`: the version badge must match
`STATUS.json`, the attack-count badge must match the rows in the harness
catalogue, and the threat-row badge must match the rows in the threat model.

The **test-count badge needed different treatment**, and the reason is worth
recording: a static `grep -c "def test_"` returns 181 while a real collection
returns 208, because of parametrised tests. A check built on the grep would
have been confidently wrong by 27. It therefore lives in
`tests/test_docs_audit.py`, where pytest exists by definition and can be asked
for a real collection - the docs-audit CI job installs no pytest.

**The check caught its own subject immediately.** Adding the two badge tests
moved the collection from 206 to 208 and the assertion failed on first run.
That is the mechanism working before it was even committed.

## Two badges that say something uncomfortable, on purpose

```
capabilities registered - 1
gated tools - 0
```

Every instinct says to omit these or to phrase them as "coming soon". They
stay, with a line under the badge block explaining that this **is** the
shipped state: the machinery is exercised before it guards anything, and every
registry entry is a reviewed code change (P3). A project whose badges only
advertise its strengths is a project whose badges nobody should trust.

`runtime deps - 0` is in the same family but points the other way: it is the
strongest single claim on the page and it is trivially checkable in
`pyproject.toml`, which is why it is linked there rather than to a proof.

## Diagrams

Every remaining ASCII diagram is now Mermaid, with explicit `classDef` dark
styling:

- **MANUAL §3.1 and §3.2** - the two topologies. The human node is highlighted
  in both, because the one thing a reader should take from a topology diagram
  here is where authority enters.
- **MANUAL §8.3** - the ledger flow, now a **sequence diagram** rather than a
  numbered list. The list showed the events; the sequence shows *who* produced
  each one, which is the part an auditor is actually reading for. The
  `attention.challenge_issued` step carries a note saying intent is recorded
  before the answer, because that ordering is a property and not an
  implementation accident.
- **ARCHITECTURE §5D.2** - the gate's data path, now a flowchart with the two
  refusal branches coloured apart from the two forward branches. The ASCII
  version buried `refusal.header_mismatch` and `refusal.tool_definition_drift`
  in indentation; the flowchart makes it visible that the path has four exits
  and only two of them forward anything.

Dark styling is explicit on every diagram rather than left to the renderer's
default, which is the standing rule in this project.

## What was deliberately not done

- **A coverage badge**: rejected. Line coverage would be high and would mean
  little; what this project can honestly advertise is the attack count and the
  threat rows, both of which are already there.
- **A "security" or "audited" badge**: rejected. Nobody has audited this. A
  badge implying otherwise would be the exact failure the truthfulness
  discipline exists to prevent.
- **Auto-generating the badge block**: rejected for the same reason the manual
  tables are hand-written with a tripwire under them. A generated badge is
  never read by its author.
