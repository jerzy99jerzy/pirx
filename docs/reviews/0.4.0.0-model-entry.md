# Pre-push review: 0.4.0.0 the model enters

```
Document:     docs/reviews/0.4.0.0-model-entry.md
Scope:        pirx/model/, pirx/proposal.py, pirx/proposer.py, pirx/session.py,
              pirx/cli.py, tests/harness/test_model_boundary.py
Disposition:  per finding - fixed / accepted with reasons / deferred
```

This is the version the earlier ones were sequenced to make safe. Through
0.3.0.0 the proposer was deterministic, so PT2 had nothing in the loop to
steer and PT6 guarded a screen carrying no model-authored sentence. Both are
live now.

## F18 - The fence tag was machine-unambiguous but human-ambiguous - **fixed**

The untrusted-prose fence uses a deterministic incrementing tag
(`~~~pirx-untrusted-N`, N chosen so the tag is absent from the enclosed
text). A parser reading the tag from the `begin` line cannot be fooled - the
same design as the approval surface's random frame, adapted because a random
boundary inside the hash preimage would destroy determinism.

But a *reader* could be. Model prose containing `~~~pirx-untrusted-0 end
model_rationale` renders as a line that looks exactly like a fence line, one
digit away from the real one, inside a block tagged `-2`. Found by
`test_a28`, which counted seven fence-shaped lines where six were emitted.

Fixed by indenting enclosed content two spaces, so no content line can even
*begin* with the fence base: unambiguous to a parser by the tag, unambiguous
to a human by the indent. The forged markers survive only as visibly indented
escaped text.

## F19 - Exact-match action selection, defended by test - **verified by
mutation**

The model's `action` is checked by exact string membership in the registry's
intent list. The tempting refactor is to trim whitespace and case-fold,
because a model occasionally returns `"Ticket.Comment "` and refusing feels
pedantic. A mutant doing exactly that was introduced;
`test_a22_near_miss_action_names_are_refused_not_normalised` went red on the
whitespace and case cases.

Recorded because the mutant is the *plausible* change - the kind a future
contributor makes to reduce friction, with a reasonable-sounding commit
message. A validator that normalises is a validator an adversary writes input
for, and the test now says so in its own name.

## F20 - No fallback on model failure - **decided, with the cost named**

When the model is unreachable or returns something outside its contract, the
run refuses. It does not quietly revert to the deterministic proposer.

The cost is real and accepted: a transient API failure stops a run that could
have produced perfectly good deterministic proposals. The reason it is still
right: the approval screen would otherwise carry no indication of which mind
produced the rationale a human is about to act on, and "sometimes a model,
sometimes not, depending on whether an HTTP call succeeded" is exactly the
kind of invisible variation that makes an approval meaningless. The mode is
also recorded per run (`proposer.mode`), so the ledger answers the question
after the fact as well.

Deterministic operation remains available - it is what happens when
`PIRX_ANTHROPIC_API_KEY` is unset - but it is a *configuration the operator
chose*, not a silent degradation.

## F21 - Two network modules now, and that is the ceiling this version
carries - **accepted with reasons**

`adapters/jira.py` (the write) and `model/client.py` (the proposal) are both
allowlisted for network reach. Every addition to that set widens what Pirx
can touch, so the set is asserted as a literal in the scrape test and a new
entry is a deliberate diff, reviewed as one.

A dedicated test also asserts that nothing under `model/` imports the grant,
capability, ledger, session, or reconciliation machinery. The model proposes
and selects; it must have no import path to anything that grants, spends, or
writes. This is a static check with the usual honest caveat - indirection
defeats it - but it makes the intended shape of the dependency graph
enforceable rather than merely documented.

## Sequencing note, worth stating once

The version plan put the harness at 0.2.0.0 and the first capability at
0.3.0.0 specifically so that this version - the one where a model gains
influence over what a human is asked to approve - landed against machinery
that was already attacked and already writing. Nine new attacks were added
here; they were cheap to write because the harness, the ledger assertions,
and the recording session already existed. Had the model come first, each of
them would have needed its own scaffolding, and the temptation to skip them
would have been proportionally larger.
