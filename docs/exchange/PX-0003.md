# PX-0003: additive fields under `additionalProperties: false`

## Evidence

cve-digest 0.7.18.0 (commit `e9e06e3`, 2026-09-24) added `epss_pending` and
`epss_percentile` to the verdict object of `cve-digest.verdict/1`, keeping the
identifier on the grounds that both fields are optional. The published schema,
`docs/schema/cve-digest.verdict-1.json`, declares that object with
`additionalProperties: false`.

The schema's own description of `epss` states the test for a breaking change:
a type change "would break a consumer validating against an earlier copy of
this schema". By that same test, the addition breaks: a consumer holding the
schema as published on 2026-08-06 and validating strictly rejects every
0.7.18.0 payload, because the new keys are properties that copy forbids.

Measured, not argued: a payload built by 0.7.18.0's `build_verdicts`,
validated with `jsonschema`'s Draft 2020-12 validator, is valid against the
schema at 0.7.18.0 and invalid against the schema as published at `ce63f26`
(2026-08-06): "Additional properties are not allowed ('epss_pending',
'epss_percentile' were unexpected)".

## What it did to Pirx

Nothing, and that is luck rather than design on either side. Pirx does not
validate against the JSON Schema; its hand-written consumer reads the keys it
knows and ignores the rest. That tolerance had no test until 0.7.4.0, which
added one because this change made it load-bearing (F63). The same
contract diff found that Pirx had in fact been refusing the producer's
payloads since 0.1.0.0 for unrelated reasons (F62) - its own defect, fixed on
its own side, recorded here only because it is why nobody noticed.

## What is asked

A decision, recorded where cve-digest records contract decisions, between:

1. **Additive is non-breaking, stated as a rule.** Consumers of `verdict/1`
   must ignore unknown properties. The schema then says so, and the
   `additionalProperties: false` on the verdict object is relaxed or
   documented as describing the producer's output rather than constraining
   what a consumer may receive.
2. **Additive is breaking under a strict schema.** The next addition takes
   `cve-digest.verdict/2` with an overlap window, per P8, and Pirx's matrix
   lists both.

Either is consistent. The current state - a schema that forbids what the
producer's own identifier policy permits - is not.

## What this entry does not do

- It does not ask for 0.7.18.0 to be reverted or re-identified.
- It proposes no schema change. If option 1 is taken, the schema edit is the
  producer's; if a change to `verdict/*` is ever proposed from this side, it
  travels as a `contract-proposal`, not as this entry.
